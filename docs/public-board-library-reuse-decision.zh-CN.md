## 结论

图语家不建立第二套公开图库服务，直接复用 CBoard 已有公开图板生态。复用前增加公开专用、版本化、有界的数据契约；Web 与微信共同使用同一 BoardDTO/TileDTO 转换语义。微信入口只位于家属“照护设置 → 图片库维护”，不进入患者表达页。

## 变动 1：公开图板 API 改为安全 bundle

- **意图：** 为 Web 和微信提供可一次获取、可验证、不会越权跟随私有子板的公开图板数据。
- **决策：** 新增 `GET /board/public/{id}/bundle` 和 `cboard-public-board-bundle v1`。服务端只遍历 `isPublic: true` 的板，循环安全，最多 100 个板和 5000 个图卡；输出移除 `email`、`_id`、`__v`，并移除指向私有或不存在子板的链接。公开列表同时移除作者邮箱。
- **理由：** 原公开列表会暴露邮箱；客户端逐板递归读取会产生多请求，也可能沿链接访问不应公开的子板。服务端公开图遍历是更可信、更容易测试的权限边界。
- **证据：** `api/helpers/publicBoardLibrary.js`、`api/controllers/board.js`、Swagger 与路由 fixture；helper/route `6 passing`、控制器单元全量 `343 passing`，Swagger YAML 可解析。
- **生效范围：** cboard-api 公开板列表和公开 bundle 读取；不改变私有板 API、公开发布、举报、登录、Settings 或数据库 schema。

## 变动 2：CBoard Web 复制复用同一公开契约

- **意图：** 保留 CBoard 原有“复制公开板”体验，同时消除递归复制私有子板的风险。
- **决策：** Web 新增 `API.getPublicBoardBundle(id)`；复制流程优先读取安全 bundle，再由共享 `publicBoardLibrary` 转成当前用户的私有 BoardDTO。兼容旧 API 时只使用当前公开列表中已知为公开的板，不再直接请求任意子板 ID。
- **理由：** 公开图板复制是 CBoard 成熟能力，应该复用而非重写；安全修复应位于数据获取边界，而不是只依赖 UI 隐藏。
- **证据：** `src/common/communicationSupport/publicBoardLibrary.js`、`CommunicatorDialog.container.js`、API client 及测试；共享转换器、容器和 API 客户端共 `48 passing`，整站 production build 成功。
- **生效范围：** CBoard Web 公开板复制和图语家共享转换核心；不改变原生板编辑器、患者表达、接收端 matcher 或账号设置。

## 变动 3：微信入口固定在家属图片库维护

- **意图：** 让家属跨分类发现和导入公开图板，同时保持患者表达流程简单、稳定且不暴露管理工具。
- **决策：** 新增平台无关 `PublicBoardLibraryPort`、Taro adapter、导入 service 和 backup 分包页面；唯一入口位于“照护设置 → 图片库维护”。支持按板名和作者搜索、查看来源与数量、确认后导入本机；同一公开来源使用稳定 ID，重复导入替换旧副本。
- **理由：** 搜索、许可判断和图库导入是低频家属维护行为，不是患者高频表达步骤。放在 backup 分包还能避免把网络搜索和转换代码加入主包。
- **证据：** `src/packages/backup/pages/public-boards`、`publicBoardLibraryService.ts`、`publicBoardLibraryPort.ts`；微信全量 `69 files / 308 tests`、TypeScript、ESLint、边界检查、production build 和输出质量门通过。
- **生效范围：** 微信家属图片库维护及本机 BoardDTO storage；不进入患者表达页，不改变接收端缺词找图、AI、语音、历史或云同步。

## 变动 4：许可证、远程图片和离线边界显式化

> 本节保留 2026-07-24 首轮边界；“不执行自动离线化”已由后续变动 6 在受限 CBoard CDN、安全代理和家属确认范围内补齐。任意外部 URL 仍不自动抓取。

- **意图：** 防止把“CBoard 上公开可见”误解为“所有图片都可自由再分发”，也不把远程 URL 冒充为已离线保存。
- **决策：** bundle 和导入 UI 明确显示逐图许可证未知；家属必须确认只导入有权使用的内容。远程图片保留来源和风险提示，不由服务端自动抓取，也不承诺断网可用。
- **理由：** CBoard 公开板没有稳定的逐图片许可证字段；服务端自动抓取任意远程 URL 会扩大 SSRF、版权和存储风险。诚实提示比静默复制更安全。
- **证据：** bundle warnings、共享 attribution 文案、微信导入确认文案和转换器测试均覆盖许可证未知与远程图片提示。
- **生效范围：** 公开板导入的提示、来源和风险边界；不改变用户对原始图片的权利，不执行 CDN 镜像或自动离线化。

## 变动 5：性能与验证门

- **意图：** 在增加低频图库能力时继续满足微信小程序包体、按需加载和构建质量要求。
- **决策：** 公开图库页面和 API adapter 只进入 backup 分包；主包不包含 `/board/public` 或 bundle 契约字符串。继续执行类型、Lint、边界、产物语法、包体和 production build 门。
- **理由：** 公开图库不是患者启动必需能力，不应拖慢主包；微信单包 2 MiB 限制和 1.5 MiB 建议线需要在每次功能切片后量化验证。
- **证据：** 未压缩 main `1,249,620 B`，距 1.5 MiB 建议线 `323,244 B`；backup `899,391 B`，距建议线 `673,473 B`；其余分包均低于建议线。现有 library 页面仍有约 438 KiB JavaScript 警告，已保留为后续异步化候选。
- **生效范围：** 微信构建、分包和质量门；不代表开发者工具官方性能扫描或真机首屏耗时已经验收。

## 变动 6：复用既有图片代理与图库恢复端口实现原子离线导入

- **意图：** 让家属导入 CBoard 公共板后，患者在断网时仍能看到已获授权且可安全获取的图片，同时避免任意 URL 代理、半导入和重复导入造成的本机文件泄漏。
- **决策：** cboard-api 新增 `GET /board/public/{id}/tile/{tileId}/image`。端点先确认板为公开板且图卡真实存在，只接受配置中的 CBoard Blob/CDN HTTPS 主机，拒绝端口、凭据、非 HTTPS 和重定向，并复用既有 Axios 上限与 Sharp `normalizePublicPictogramImage` 输出 300px 有界 PNG。bundle 只附加稳定 `offlineImagePath`，不替换原始图片地址。微信复用 `PictureLibraryArchivePort` 的下载、二进制读取、恢复目录、写入和清理事务：默认最多 200 张、单图 2 MiB、总计 20 MiB，全部成功后才保存 BoardDTO；任一失败则删除本轮暂存并保持图库不变。家属再次确认后才可退回“仅网络链接”导入；重复导入提交成功后再清理不再引用的旧本机图片。
- **理由：** 微信 `downloadFile` 只能访问公众平台白名单域名，直接下载任意公共板外链既难配置也会扩大 SSRF、内网访问和内容风险。cboard-api 已有 Axios、Sharp、图片字节/像素上限，微信也已有图库 ZIP 恢复事务，复用这些成熟边界比自研下载器、缓存数据库或开放代理更小、更可靠。把原始 URL 保留在 bundle 中还能保证 CBoard Web 继续按原语义复制，不受微信离线元数据影响。
- **证据：** API 公开板图片/helper/route 聚焦 `12 passing`，全部无数据库控制器与 passport 回归 `350 passing`，Swagger 可路由，生产部署模板通过；CBoard Web 共享转换 `2 passing`，证明忽略 `offlineImagePath` 并保留原图地址；微信定向 `26 passing`、全量 `69 files / 312 tests`、TypeScript、ESLint、`197 app / 30 CBoard core` 边界、production build 与 `7/7` 质量门通过。产物中的公开板代理字符串只存在于 backup 分包；未压缩 main `1,249,620 B`，backup `904,189 B`，均低于 1.5 MiB 建议线。
- **生效范围：** cboard-api 公开板中已配置 CBoard 图片主机的只读 PNG 代理、微信家属图片库的公共板离线导入/回退/重复导入清理，以及 Web 对新 bundle 元数据的向后兼容；不进入患者表达页，不代理任意外部主机，不改变图片许可证、公开发布、缺词在线补图、默认板、matcher、语音、AI、历史或云同步。

## 变动 7：复用图符搜索的有界缓存模式保护公开图片端点

- **意图：** 防止重复导入、并发手机请求或恶意重复访问让公开图片端点反复下载同一上游文件并执行 Sharp，放大 CDN 流量、CPU 和内存消耗。
- **决策：** 复用 `pictogramSearch` 已验证的 Map LRU 与 in-flight promise 模式：同一公开板、图卡和原始图片 URL 的并发请求合并为一次；成功 PNG 缓存 5 分钟，最多 100 项且总字节不超过 20 MiB，按最近使用顺序淘汰。每次读取缓存前仍重新查询 `isPublic: true` 的板和图卡，并重新校验当前 URL 与主机白名单；板下架、图卡删除或 URL 变化不会只凭旧缓存继续提供内容。失败不缓存。
- **理由：** `Cache-Control` 只能帮助守规矩的客户端，不能保护首次请求、并发请求或绕过缓存的调用者。项目已有短期 LRU 和并发合并模式，沿用它比引入 Redis、另一套缓存依赖或无界 Map 更小；总字节上限比仅限制条目数更能约束图片缓存内存。
- **证据：** 新测试证明并发请求只触发一次 HTTP/归一化、TTL 内复用、过期后重新获取；公开板图片/route 聚焦 `13 passing`，cboard-api 无数据库控制器与 passport 全量 `351 passing`，Prettier 与差分检查通过。
- **生效范围：** 单个 cboard-api 进程内的公开板图片代理缓存和并发合并；不跨进程共享，不缓存失败，不改变公开权限、主机白名单、图片字节/像素上限、客户端 BoardDTO 或微信本机文件。真实多副本部署仍依赖上游/CDN 和每实例独立有界缓存。
